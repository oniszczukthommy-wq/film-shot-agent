# 设计取舍

这份文档解释 Shot Agent 为什么长成这样。它不是功能清单，而是一串"为什么不做那个"。

---

## 一、先定死边界

**这是一个面试演示，不是一个要上线的产品。** 这句话决定了后面所有取舍：

1. **必须在笔记本上一条命令跑起来** —— 所以没有 Docker、没有外部数据库、没有构建步骤。
2. **必须每次都演示出同样的结果** —— 所以不让大模型参与决策。
3. **必须经得起追问"这数据哪来的"** —— 所以素材全部是 CC BY 授权的开源电影。

---

## 二、为什么砍掉 Jellyfin

上一版是给 Jellyfin 用户的：登录走 Jellyfin、片库读 Jellyfin、播放走 Jellyfin 票据。
对真实用户是对的，对演示是灾难——面试官电脑上没有你的 NAS，代码里 35/60 个文件绑着 Jellyfin。

所以改成：**片库就是 `data/library/raw/` 下的几个文件**。这一刀砍掉了三个模块
（认证、播放票据、进度同步），换来的是"clone → ingest → 打开浏览器"。

**如果被问到"真实场景怎么办"**：片库来源抽象成 `Title.source_file`，接 Jellyfin/本地/NAS
只是换一个写 `Title` 的 ingest 脚本，服务层不用动。这个说法不是狡辩——`adapters/ffmpeg.py`
确实只认路径。

## 三、借了什么，没借什么

参考的两个产品：**33台词**（台词检索 + 本机切片）和 **ShotDeck**（镜头库 + 分面 + 参考板）。
反推出来的机制在 `../ShotDeck-REA分析/` 和 `../33tc-REA分析/` 里，这里只说取舍。

### 借了

| 机制 | 来源 | 在这里怎么实现 |
| --- | --- | --- |
| 路径式查询（查询状态 = URL） | 两家都有 | `/browse/color_temp/cool/brightness/dark` |
| 分面计数（选它剩多少） | ShotDeck | `facet_counts()`，计算时排除本维度 |
| 三级配色检索 `shade~distance~proportion` | ShotDeck | 目标色 + 色差容差 + 最小占比 |
| 台词带前后句 + 高亮 | 33台词 | `search_lines()` 返回 prev/next/spans |
| 本机 ffmpeg 切片 + 多档 GIF | 两家都有 | `clips.py`，MP4 + 5 档 GIF |
| 参考板 | ShotDeck 的 Deck | `Deck` / `DeckItem`，可放镜头和台词 |

### 没借，以及为什么

| 不借 | 原因 |
| --- | --- |
| **22 个人工筛选维度** | ShotDeck 有标注团队，我没有。硬做会得到一排永远空着的字段。只做机器能算的 7 个维度 + 取色，反而每个都是满的。 |
| **yt-dlp 下载 / 第三方站点截图** | 违反平台条款且有法律风险；演示也完全不需要——CC BY 电影照样能切出生动的片段。 |
| **服务器端转码集群** | 单机演示，本机 ffmpeg 足够；带缓存后同一镜头只渲染一次。 |
| **账号 / 团队 / 分享外链** | 单人本机演示不需要；而且整板影视截图的外链是版权风险面。 |
| **客户端 MD5 签名 / API Key** | 没有多端、没有第三方调用方，加了只是自欺欺人。 |

## 四、几个具体的技术决定

### 调色板用 k-means，不用平均色

平均色会把"一半蓝天一半火焰"糊成一片灰。k-means 出来的 5 个主色 + 占比，
才能支持"这个蓝色至少占画面 40%"这种检索。

实现上没引 numpy：64×36 = 2304 像素、k=5、8 轮迭代，纯 Python 跑几十毫秒，
不值得为它加一个二进制依赖。

### 档位按分位数切，不写死阈值

第一版把 `亮度 > 0.6 = 亮调` 写死，结果 120 个镜头里 110 个判成"高对比"——因为电影本来
就对比度高，固定阈值等于没有筛选。

改成**按本库三分位切**后，每个档位都是 1/3。代价是"档位含义随库变化"，所以库里存了
原始浮点值（`brightness` / `contrast` / `saturation`），换库重算即可。

### 台词和画面用时间轴对齐，不建关联表

`cue.start_ms` 落在哪个 `shot.start_ms..end_ms` 区间，就是那句话的画面。
不需要人工标，也不需要额外的 join 表——一次范围查询就够了。

### Agent 是规则，不是模型（本地层）

> 2026-10 补充：这句话只对本地镜头检索成立。旁边新增的「问片」层是研究型 agent，模型负责编排工具，但引用、评分、观看渠道都有确定性校验，详见 [`问片设计.md`](问片设计.md)。

`"找冷色调、暗一点的镜头"` → `{color_temp: cool, brightness: dark}`。

规则有明确的代价（不懂"雨夜车窗"这种比喻），但换来了三件事：
演示可复现、零延迟、**trace 可以被追问**。而 trace 面板恰好是面试里最能聊的东西——
"这里为什么调这个工具""为什么只返回 31 条"都能对着说。

真接模型的话，正确的做法是让它只产出**受约束的意图标签**，而不是让它决定返回哪些镜头。

### 拼图用 xstack，不用 image2 + tile

第一版用 `-i %04d.jpg -vf tile=3x2`，结果输出全黑：image2 序列 + 空格子（补黑图）时
tile 会把不满的格子当成还没到齐，最后刷出空帧，而且 `returncode` 仍然是 0——
静默失败。

改成显式 `xstack=inputs=N:layout=...`：输入几张就拼几张，布局位置自己算，
不满的格子交给 `fill` 颜色。确定、可测、不会静默出错。

教训记在这里：**ffmpeg 用 `-loglevel error` 时，失败可能只体现在像素上，不在返回码上。**
所以导出相关的测试都要断言"产物非空且尺寸正确"，不能只看 returncode。

### 测试不碰 ffmpeg

`tests/test_clips.py` 把 `ffmpeg.make_clip` 换成假实现，验证的是"缓存命中"和"格式化"这些
真正属于业务的逻辑。46 个测试跑 0.3 秒，不联网、不需要 ffmpeg 二进制。

## 五、前端为什么长这样

视觉语言不是我自己拍的，是按一份给定的设计系统（"soft daylight notebook"）落地的，
所以下面这些是**照做**而不是偏好：

| 规则 | 落地方式 |
| --- | --- |
| 画布 #ebf5ff / 卡片 #fafdff | 页面背景天蓝，所有卡片骨白——深度只靠这一级色差，不用阴影 |
| 唯一深色填充 #181d27 | 只有主按钮和选中态用，别处一律留白 |
| 标题固定 500 字重 + 紧字距 | 大标题 -0.02em，正文 -0.01em；整个系统没有 700 |
| 32px 卡片 / 24px 图片 / 9999px 药丸 | 圆角只有这三档 |
| 蓝色只做强调 | 渐变描边、行内高亮、`.line-zh` 的中文翻译；**不做按钮填充** |
| 柔和粉彩只做色块 | 薄荷色给"从这句开始播"，粉蓝给药丸标签，薰衣草/蜜桃给背景光斑 |
| 尽量少动 | 0.3–0.65s，`cubic-bezier(0.16, 1, 0.3, 1)`，只做轻微上浮 |

两个刻意的破例，都有理由：

1. **主体内容是摄影**。设计系统说"不要照片，用 3D 插画"，但这产品就是镜头库，
   缩略图必须是真实画面；所以装饰部分改用 CSS 粉彩光斑代替 3D 插画，把"照片"全部收敛到内容区。
2. **正文不放 148px 标题**。那是首页 hero 的尺寸，工具页用 32px（heading），
   否则一屏看不到结果——设计系统里"显示级字号"和"工具可用性"冲突时，可用性优先。

## 六、如果要继续做，下一步是什么

按性价比排：

1. **视觉模型打标**（景别 / 构图 / 人数 / 情绪）—— 补上 ShotDeck 那 22 维里最难自动化的部分。
   本地跑一个小模型，产出写回 `Shot` 的新列即可，检索层不用改。
2. **向量检索**（以图搜图）—— 每镜头存一个 embedding，SQLite 里做暴力余弦相似度在
   几千个镜头规模够用；上万再换 `sqlite-vec`。
3. **参考板导出**（PDF / 拼图）—— ShotDeck 的 `exportdeckajax` 对应物，面试演示很出片。
4. **片库接入层** —— 把 ingest 写成插件，接 Jellyfin / 本地目录 / 网盘。

## 七、已知的坑

| 坑 | 现状 |
| --- | --- |
| 取色检索是"先 SQL 再 Python 过滤" | 244 个镜头没问题；上万镜头要预建颜色索引表 |
| 场景切分阈值固定 0.35 | 快节奏片子会切太碎；按片自动调阈值更好 |
| 字幕只支持 SRT/ASS 且需与影片同长度 | 时间轴对不上时台词↔画面对齐会偏 |
| 中文分词没做 | 台词检索是子串 + 词元匹配，"机器人"能搜到、"机器手"搜不到"机械手臂" |
