# 问片设计

`/ask` 是 2026-10 加的研究层。它回答的不再是"我本地这两部片里有什么镜头"，而是"任意一部片值不值得看、在哪看、这句台词/这个画面出自哪"。

## 一、和旧层的关系

| | 镜头库 `/` | 问片 `/ask` |
| --- | --- | --- |
| 数据 | 本地 SQLite，244 个镜头、76 条台词 | 联网 + TMDB |
| 决策 | 规则（可复现） | 模型编排工具（研究型） |
| 输出 | 确定的镜头/台词/切片 | 带证据和置信度的答案 |
| 失败方式 | 查不到就是 0 条 | 查不到要说"没查到" |

旧层不动。问片不是替代，是旁边加的一层。

## 二、一次请求发生什么

1. 用户问题进 `services/research.py`，最多 6 轮工具调用。
2. 模型可选六个工具：`search_web`、`movie_facts`、`where_to_watch`、`reviews`、`search_quote`、`identify_scene`。
3. 每次工具结果写进 `ResearchContext`：引用表、URL→摘要、URL→评分事实、URL→观看事实、trace。
4. 模型只负责"下一步查什么"和"怎么组织语言"。
5. 最后用 JSON mode 再调一次模型，产出 `answer / titles / citations / caveats / followups`。
6. 确定性代码做最后一遍清洗（见下）。

如果模型一轮工具都没调，代码会强制补一次 `search_web`——"联网搜索一定要加"不能靠提示词保证。

## 三、三道证据闸门

### 1. 引用白名单

`ctx.citations` 只装工具实际返回过的 URL。最终 `citations`、每张卡片的评分/评论/观看链接都必须在这个集合里。模型写了一个集合外的 URL，直接丢弃，不提示。

### 2. 评分反查

- TMDB 的结构化评分：`ctx.rating_facts`，以工具值为准，模型不能改分数。
- 搜索来的评分：URL 必须是豆瓣/IMDb/烂番茄/Metacritic/Letterboxd/TMDB，且分数数字必须出现在该 URL 的标题或摘要里。否则丢弃。
- 结果：博客里写的"豆瓣 9.3"不会变成一张"豆瓣 9.3"的卡；它最多出现在 answer 文案里，并带"第三方转述"的 caveat。

### 3. 观看渠道反查

- 平台名和 `免费/可能免费/会员/付费` 标签只能来自 `ctx.watch_facts`（TMDB 或 `where_to_watch` 的确定性推断）。
- 搜索结果的"免费"一律降级为"可能免费"；只有 TMDB 的 `free` 才写"免费"。
- 平台搜索页（`/so/`、`/search`、`?q=`）不算影片链接，直接过滤。
- 平台白名单：B站、爱奇艺、腾讯视频、优酷、芒果TV、1905、YouTube、Internet Archive、搜狐、乐视、WeTV、Viki、Netflix、Prime Video、Disney+、JustWatch。

## 四、搜索与模型

- 模型：任何 OpenAI 兼容的 `/chat/completions`，默认 DeepSeek。
- 搜索：有 `FILM_AGENT_SEARCH_API_KEY` 时用 Tavily/Brave；没有时 DuckDuckGo HTML → 360 搜索兜底。
- 免费兜底会被限流，表现是"工具返回 0 条"。这时答案应该说不确定，而不是编。
- 多个独立查询并行执行（`ThreadPoolExecutor`），把 3 条搜索的耗时压到最慢那条。

## 五、明确不做

- 不抓豆瓣/IMDb 页面全文。豆瓣没有公开 API；抓取违反条款、反爬也不稳定。
- 不返回盗版站、网盘、磁力、种子。
- 不承诺"模糊镜头"唯一答案。没有全电影镜头库，文字描述只能给候选。
- 不把模型记忆当事实。没有工具证据的评分、链接、年份不进卡片。

## 六、下一步

1. 配 TMDB Key：结构化评分 + JustWatch 渠道，评分卡会稳定很多。
2. 配 Tavily/Brave Key：搜索不再依赖会被限流的免费兜底。
3. 10 条真实问题打分：找片 Top1、台词命中、镜头候选命中，按结果再调 prompt 和工具。
4. 二期再评估截图识别（视觉模型 + 以图搜图）和多人访问控制。
