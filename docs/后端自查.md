## 二、修掉的两个 bug

### 1. 非数字查询参数直接 500

```
GET /api/shots?limit=abc          → ValueError: invalid literal for int()
GET /api/shots?distance=x         → 同上
```

`int(params.get(...))` 没有兜底。改成统一的 `_int_param()`：解析失败回到默认值再夹到合法区间。
**这条最容易被面试官随手点出来**——URL 里敲个字母就白屏。

### 2. 非法 hex 让路径式查询崩掉

```
GET /api/browse/shade/..%2F..%2Fetc → ValueError: invalid literal for int() with base 16: '..'
```

`hex_to_rgb()` 假定输入一定是合法十六进制。加了唯一的校验入口 `look.normalize_hex()`，
`parse_filters` 和查询参数两条入口都走它；非法值直接当作"没有颜色筛选"，不猜。

### 3. 附带修的：媒体路径前缀匹配

```python
# 原来
str(path).startswith(str(thumbs_root))     # "thumbs-evil/x.jpg" 也能通过
```

改成 `_safe_media_path()`：先拒绝含 `/`、`..` 的名字，再用 `Path.is_relative_to()` 判定。
虽然实际很难利用（还得文件真实存在），但这种"看起来安全其实不是"的写法不该留。

## 三、没修但要知道的边界

| 项 | 现状 | 什么时候会坏 |
| --- | --- | --- |
| 台词检索是 Python 全表打分 | 76 条 → 5 ms；每条查询遍历所有 cue | 上万条 cue 时要换 SQL `LIKE` + 索引，或上 FTS5 |
| 筛选先全量取出再排序分页 | 244 条无所谓 | 十万级镜头要改成 SQL `ORDER BY`/`LIMIT` + 预建颜色索引 |
| 取色筛选用 Python 过滤调色板 JSON | 同上 | 同上；且分面计数也要先算一遍命中集 |
| 读接口会写埋点 | 每次搜索 `+1` 计数，靠 WAL | 高并发写会有锁竞争，届时把计数挪到内存+批量落盘 |
| 没有鉴权 / 限流 | 本机单用户演示，故意不做 | 一暴露到公网就必须补 Token + 限流 |
| `/api/decks` 无归属概念 | 单人，deck 全局可见 | 多人要加 `owner_id` 和隔离 |

这些都是**刻意的**：当前规模下行得通，写清楚比假装没有好。

## 四、这个后端给前端留的接口形状

前端只需要三类东西：

1. **读**：`/api/facets`（带每个选项的计数）、`/api/shots`、`/api/lines`、`/api/titles`、`/api/shots/{id}`
2. **写**：`/api/decks` 系列（建板、加项、删项、删板）
3. **媒体**：`/media/thumbs/{name}`（缩略图，带 1 天缓存）、`/media/video/{slug}`（支持 Range）、
   `/api/shots/{id}/clip?fmt=mp4|gif-xs…xl`、`/api/decks/{id}/collage`

所有检索参数既可以用查询串（`?color_temp=cool`），也可以走路径（`/browse/color_temp/cool`）——
后者是给人分享用的，前者给程序用。

`/docs` 里能看到完整的 OpenAPI，可以直接生成 TS 客户端。
